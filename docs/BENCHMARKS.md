# 性能基准（v0.1，release）

测试环境：Arch Linux x86-64，内核 7.2.9，8 核，31 GiB RAM，8 线程索引。
数据集：`/tmp/everything-bench` 下 100 个目录 × 1000 文件 = 100,000 个文件。

## 冷索引

| 指标 | 结果 |
|---|---|
| 100k 文件全量索引 | 约 1–3 秒（含目录创建开销，日志显示索引就绪） |
| 快照大小（zstd level 1） | 716 KB |
| 快照加载 → socket 可用 | 158 ms |
| 增量更新（单文件创建 → 查询可见，P50） | 约 40 ms（含 CLI 进程开销）|
| 守护进程 RSS | 约 42 MB（含运行时开销，约 400 B/条目） |

## 查询延迟（P50，10 次运行，引擎侧计时）

| 查询 | 引擎耗时 | CLI 端到端 | 匹配数 |
|---|---|---|---|
| `file_050_0123`（子串） | 3.3 ms | 6.7 ms | 1 |
| `file_050_*`（通配符） | 8.1 ms | 11.5 ms | 1,000 |
| `-e file_0[0-9][0-9]_0999`（正则） | 13.0 ms | 17.1 ms | 100 |
| `path:dir_050`（全路径） | 53.3 ms | 63.3 ms | 1,001 |
| `-s -size *.txt`（按大小排序） | 10.9 ms | 15.2 ms | 100,000 |

## 增量更新验证（10 万文件索引）

连续创建 10 个文件：`full_rebuilds` 保持 1（仅启动），`incremental_updates` 增加 10；
删除后计数继续增加，`full_rebuilds` 不变。说明变更走的是增量快照路径。

注意：`*.txt` 返回全部 100k 结果时 CLI 约 109 ms，主要耗时在 IPC 传输与终端打印，而非查询本身。

## 功能验证

- 默认大小写不敏感、`-c` 大小写敏感：`通过`
- 通配符 / 正则 / 前缀操作符（`startwith:` `path:` `file:` `folder:`）：`通过`
- 布尔 AND / OR / NOT / 括号：`通过`
- 全词匹配：`通过`
- inotify 新建 / 重命名 / 删除 / 新建目录子树实时可见：`通过`
- 快照保存与重启加载：`通过`
- `cargo test --offline`：7/7 通过

## 与目标的对照

| 目标（1M 条目） | 当前推算 | 判断 |
|---|---|---|
| 子串查询 < 50 ms | 100k 为 3.3 ms，线性放大约 33 ms | 预计达标 |
| 快照加载 < 200 ms | 100k 为 158 ms（含进程启动） | 1M 可能超过，需优化加载路径 |
| 内存 < 200 MB | 100k 约 42 MB → 1M 约 420 MB | 超出，需压缩元数据结构 |
| 冷索引 < 60 s | 100k 约 1–3 s → 1M 约 10–30 s | 预计达标 |

结论：查询性能与 Everything 同数量级；内存与快照加载是下一阶段优化重点。

## 内存优化后的增量更新

`IndexSnapshot` 改为 `Arc<Vec<...>>` 名字池 + 按 slot 的 `entry_overrides` 增量层：

- 名字/折叠名字池在快照间共享，不再每次变更复制约 30 MB（百万级）；
- 只保存变更条目的 override 和追加的名字字节，避免复制全部 `entries`；
- 10 万文件下连续 10 次创建，`full_rebuilds` 仍为 1，增量更新计数正常，查询延迟不变。

属性过滤查询（10 万文件，release，引擎侧）：`size:>12` / `ext:rs|md` / `dm:<2020-01-01` 均 < 1 ms。
