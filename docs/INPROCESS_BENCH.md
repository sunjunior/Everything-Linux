# 进程内架构 vs 守护进程 + IPC 基准

对比分支：`feature/inprocess-engine`（进程内 `LocalEngine` SDK）与 `main`（守护进程 + Unix socket IPC）。

## 环境与方法

- Arch Linux x86-64，8 核，31 GiB RAM；索引 939,137 个文件（根 `/home/sunjunior`）。
- 两侧使用同一份快照（24 MB），关闭自动根目录。
- 查询延迟取 10 次中位数；IPC 为 Rust 客户端 `client_call`，进程内为 `LocalEngine::search_paths`（包含路径重建与转成 `String`，与 GUI/CLI 消费路径的方式一致）。
- GUI 使用当前 X11 会话启动，测窗口出现时间与稳定后 RSS/PSS。

## 查询延迟

| 查询 | IPC 引擎 | IPC 端到端 | 进程内端到端 | 差值 |
|---|---:|---:|---:|---:|
| `*.rs`（5000 条） | 11.5 ms | 15.9 ms | 14.8 ms | -1.1 ms |
| `main.rs`（77 条） | 8.8 ms | 10.8 ms | 8.6 ms | -2.2 ms |
| `zzzzz-nomatch`（0 条） | 6.9 ms | 10.5 ms | 6.7 ms | -3.8 ms |
| `path:everything-linux`（5000 条） | 50.2 ms | 57.9 ms | 58.9 ms | +1.0 ms |
| `*.txt` + 按大小排序（5000 条） | 7.7 ms | 15.0 ms | 11.4 ms | -3.6 ms |

结论：IPC 端到端额外开销约 **2–8 ms**；进程内模式在普通/空结果/排序查询上节省约 **1–4 ms**，全路径查询因引擎本身占主导（约 50 ms）没有收益。

## CLI 一次性调用

| 模式 | `*.rs` | 无命中 |
|---|---:|---:|
| 已运行守护进程 + IPC | 20.6 ms | 10.8 ms |
| `everything --local` | 168.1 ms | 157.3 ms |

进程内 CLI 每次都要加载 24 MB 快照，一次性命令明显更慢；只有长期驻留的前端（GUI）才适合进程内模式。

## 内存、进程与启动

| 指标 | main（daemon + GUI） | 进程内 GUI |
|---|---:|---:|
| 进程数 | 2 | **1** |
| RSS | 76.9 + 113.8 = **190.7 MB** | **186.3 MB** |
| PSS | 16.2 + 122.1 = **138.3 MB** | **125.7 MB** |
| GUI 二进制 | 5.5 MB（内嵌 daemon） | **3.5 MB** |
| 窗口出现 | 558 ms | **536 ms** |
| 引擎加载（含 watch） | 约 0.9 s | 0.51 s（SDK 示例） |

内存基本处于同一水平，进程内模式少一个进程、PSS 略低、GUI 包体更小。

## 建议

- IPC 开销相对查询引擎很小，当前“守护进程 + IPC”架构对 CLI/多客户端更合适，不建议整体替换。
- 若只追求 GUI 体验，可考虑 GUI 内嵌引擎（单进程、包体更小、普通查询快 1–4 ms），但需明确 CLI 与 GUI 同时使用时的索引归属。
- 更大的性能空间在全路径查询（约 50–60 ms）与 GUI 结果列表渲染（每次最多 5000 条），而不是 IPC。
- `LocalEngine` SDK 可保留，便于其他 Rust 程序直接嵌入索引能力。

## 优化后（slots 惰性渲染 + Top-N）

在融合版基线上继续优化：

- 查询只返回 slot id，GUI 只为可见行按需渲染路径，不再为 5000 条结果生成路径字符串；
- 已知 limit 时先用 `select_nth_unstable_by` 选出 Top-N，再对 N 条排序，避免宽匹配时全量排序；
- ListStore 直接存 `u32` slot，而不是 5000 个 `String`。

| 查询（5000 条结果） | 旧融合 `search_paths` | 新融合 `search_slots` | 变化 |
|---|---:|---:|---:|
| `*.rs` | 14.8 ms | **8.9 ms** | **-40%** |
| `*.txt` + 大小排序 | 11.4 ms | **7.5 ms** | **-34%** |
| `path:everything-linux` | 58.9 ms | **51.1 ms** | **-13%** |
| `main.rs`（77 条） | 8.6 ms | 8.6 ms | 持平 |
| 无命中 | 6.7 ms | 6.9 ms | 持平 |

GUI 侧另外测得：

- 5000 行 ListStore：`String` 6.9 ms → `u32` 5.8 ms（约 -16%）；
- 实际 GUI 输入 `*.rs` 后状态栏显示 10.6 ms（旧融合版同查询为 14.8 ms，约 -28%）；
- 稳定 RSS 仍约 186 MB，无明显内存回退。

综合估算：宽结果查询端到端提升约 **28–32%**，全路径查询约 **13–15%**，少量结果/无命中查询基本不变（已到扫描底噪）。如果按“所有查询平均”计算，提升幅度取决于大结果查询占比；按“大结果/宽匹配”目标，已达到并超过 15–20%。

## raw mmap CLI 原型

为验证“融合版 CLI 能否追平 daemon”，新增 70 MB 的 raw 只读快照（entries 40 B、名字池、折叠名池、live 位图），CLI 直接 mmap 后查询，不再解码 zstd、解析 100 万条记录或重建父子链。

| CLI 查询（5000 条） | 当前 GitHub（daemon 热） | 融合 CLI（zstd 快照） | 融合 CLI（raw mmap） |
|---|---:|---:|---:|
| `*.rs` | 21.0 ms | 164 ms | **20.7 ms** |
| `main.rs`（77 条） | **11.5 ms** | 164 ms | 16.8 ms |
| 无命中 | **10.8 ms** | 157 ms | 13.7 ms |
| `path:everything-linux` | **60.8 ms** | 164 ms | 66.2 ms |
| `*.txt` + 大小排序 | **15.4 ms** | 164 ms | 19.6 ms |

无 daemon 的冷启动单次调用：当前版本约 896 ms，raw CLI 约 21 ms。

raw 引擎在常驻进程内热查询为：`*.rs` 10.8 ms、`main.rs` 10.1 ms、无命中 7.7 ms、全路径 55.0 ms；相对 Store 引擎（8.9 / 8.6 / 6.9 / 51.0 ms）有约 1–4 ms 的 mmap/枚举访问开销，CLI 还要额外承担进程启动与首次 page fault。

**结论：raw CLI 在宽结果查询上已与热 daemon 持平，但小结果和全路径查询仍慢 3–6 ms。按“所有场景持平或更好”的条件，目前不建议把所有发行版切换到融合架构。**

## 后台换根（融合版）

`LocalEngine::set_auto_root` 现在先构建一个全新的 Engine（扫描新根、挂 watch、写快照），期间旧 Engine 继续服务查询；新索引就绪后原子替换。GUI 为每行结果记录 generation，换根后旧行自动隐藏，并重新执行当前查询。

实测：旧索引为 `/home/sunjunior`（94 万文件），重建同一根耗时 **2378 ms**；重建期间持续查询的延迟：

- 中位数 **11.2 ms**
- P95 **16.4 ms**
- 最大 **21.6 ms**

对比修改前：换根会持有引擎锁约 2.4 s，期间查询全部阻塞。换根完成后 `files=942009`、`a-only=0`，查询结果正确。代价是重建期间内存约翻倍（新旧索引同时存在）。
